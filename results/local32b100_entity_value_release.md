# 第三类 bad case 深挖：已提交但「实体/数值错」——verifier 对部分匹配/自有算术放行

> 数据：`results/local32b100/`（本地 Qwen3-32B 策略+verifier，随机 100 条，max_turns=100）
> 方法：逐轮重建代表轨迹 + 对 32B 做「同证据异指令」能力对照 + 算术复算。
> 回答的问题：已提交 36 错里，策略产出**具体但错误**的实体/数值时，为什么 32B verifier 还判 `supported` 放行？归因于配置 / ESR 方案 / 代码偏差？

---

## 一、先划界：第三类不是独立同质一类，是前两类之间的一条模糊带

按提交答案性质把 36 错拆开：

| 答案性质 | 例数 | 归属 |
|---------|------|------|
| (a) 纯拒绝措辞（`Not found` / `Insufficient`…） | **16** | 第二类（拒绝式放行）|
| (b) 拒绝措辞里嵌了实体名（`Martha Argerich's mother's full name is unknown`） | ~6 | 第二类的变体 |
| (c) **具体实体/数值，但答案错误** | **~11–13** | **本类（第三类）稳定内核** |
| (d) 判分粒度伪影 | 2 | 380 实为正确；1139 近邻术语 |

第三类不像前两类有单一机械根因，它其实是**「策略选错实体 + verifier 认可」的组合**，而 verifier 的认可又有两种不同内核。逐条读轨迹后把它裂成两个子机制 + 一个伪影。

## 二、子机制 A：verifier 对「表面/部分匹配」放行（占多数，~9–11 例）

策略产出具体实体，但那个实体**不是问题真正要的**；证据里恰好浮出这个实体（或近似候选），verifier 看"名字对上了"就判 supported。代表：

| qid | ANS(具体但错) | GOLD | verifier 的 rationale（放行理由）|
|-----|--------------|------|------|
| 416 | `Kelsee Baranowski` | `Hsiang Sing Naik` | "证据明确提到 Kelsee 是致谢第三个人…与答案一致"→ 找"一个致谢第三人"而非"那篇论文的第三人" |
| 580 | `Friends` | `You're the Worst` | "证据确认 Friends 是情景喜剧，与题干情节点吻合"→ 把题干情节点表面映射到 Friends |
| 664 | `Bolton Wanderers` | `FC Krasnodar` | "比赛数据与问题一致，答案正确指出博尔顿"→ 把冲突描述表面认给博尔顿 |
| 583 | `2019 Grant Recipients` | `New mural…Cuore` | "证据提到 2019 Grant，与背景一致"→ 主题相近即放 |
| 1012 | `21 August 2020` | `22 September 2023` | "证据确认 In a Dream 于 21 Aug 2020 发行"→ 对上了"EP+日期"，不是题目要的那一题 |
| 408 | `Atari 128KB BASIC` | `Atari 130XE` | "第一台是 Atari 计算机…与答案一致"→ 对上"Atari"，没锁到具体机型 |
| 1203 | `Petri Alanko & Martin S.A.` | `Cassano Thruston` | "Control 的作曲人是 P&A/MSA，直接支持"→ 对上了"作曲人词组"，不是题目问的那位 |

**机制**：证据文本确实出现了答案所指的**主语/近似项**，verifier 只做"证据是否点名答案所述实体/事实"的**表面核对**，而**不做"这个实体是否是题干多约束条件组合下唯一解"的深度校验**。题干是一串约束（情节点/年份/身份）；任何"满足部分约束、或只是名字恰好出现"的候选都可能被放行。

**q580 全轨迹（5 动作，首 verify 即 supported）**
```
[t1] SEARCH  'TV series with specific plot points: season1 首集日期考研、season3 末集室友牺牲、season4 女主与故人重逢'
[t2] OPEN    65004 → e1（Friends 维基页）
[t3] UPDATE  answer='Friends'
[t4] VERIFY  supported   ← 证据"确认 Friends 是情景喜剧，与题干情节点吻合"
[t5] SUBMIT  'Friends'
```
但我的**能力对照**显示：32B 被塞进"必须是唯一目标 + 逐条核对题干约束 + 检查季数"指令后，会立刻指出 **"Friends 有 10 季，与题干'少于 10 季'矛盾"、'情节点不对齐'** → needs_revision。**即：证据里那条能推翻 Friends 的季数约束就摆在那，es 现行指令从不要求 verifier 逐条核对所有题干约束，32B 就漏了。**

## 三、子机制 B：verifier 自算算术出错（2 例，纯能力）

这类 verifier 不只是"核"答案，而是**自己执行数值推导**，算术/舍入错了还不自知：

| qid | ANS | GOLD | 证据关键数 | 复算 |
|-----|-----|------|-----------|------|
| 624 | **66%** | **65%** | Grants=28498, 总=43487 | **28498/43487 = 65.53%**，verifier 四舍五入到 66%，认可 |
| 778 | **22** | **21** | Maye 19 岁时生 Elon；Tosca 10 岁获母建议 | 差一，verifier 自算 22 并认可 |

**q778 全轨迹**
```
[t1] SEARCH  'CEO 90年代中创立非洲SIDS...'
[t2] OPEN    68457 → e1（Musk 家族树）
[t4] VERIFY  needs_revision g1："提到 Maye 生 Elon 的年龄，但没直接给 Tosca"
[t5] SEARCH  'Maye Musk age when she gave birth to Tosca Musk' → 开 54887(e2)
[t7] UPDATE  answer='22'
[t8] VERIFY  supported  ← rationale 自己做年龄推算并认可"22"
[t9] SUBMIT  '22'
```
**机制**：`VERIFY_INSTRUCTION` 把"能否被证据支持"的判定权**整个押给 model 的数值推理**，而 32B 的多步数值推导（除法、舍入、年龄差）可靠性不足，**没有第二道确定性复算兜底**。这类不是"选错实体"，是**算错数还被自认可**。

## 四、判分粒度伪影（2 例，不算真错）

- **380**：ANS=`46.30 cm`，GOLD=`46.30 centimetres`——**本质上同一个数**，是 ExactMatch 判分把"cm/centimetres"当成不同串导致的伪错。它不该在 bad case 里。
- **1139**：ANS=`ulwaluko`，GOLD=`Ukudlanga`——同一 Xhosa 传统割礼话题的近邻术语，判分按完全相等没命中。属判分敏感，非机制错误。

这两例提示一个 caveat：第三类的"错"有**判分粒度噪声**，真正的机制性错误是上述 ~11–13 例（A 为主、B 为次）。

## 五、归因：配置 / 方案 / 代码？ 三层判定

| 层 | 判定 | 依据 |
|----|------|------|
| **实验配置** | 不是主因 | 与类别无关；任意配置下 verifier 都会按现行指令做表面/算术校验 |
| **ESR 方案** | **主因（规格软，分两层）** | 见下 1/2 |
| **代码-ESR 偏差** | **无偏差** | api/本地 VERIFY_INSTRUCTION 逐字节相同，release 全在既有 environment.py 的 verify 协议内 |

**方案规格的两处软，分别喂 A / B 两个子机制：**

1. **`VERIFY_INSTRUCTION` 只要求"证据点名答案所述实体/事实"，缺『必须是题干读多约束下的唯一目标 + 逐条核对所有约束 + 身份消歧』** → 喂子机制 A（表面/部分匹配放行）。能力对照证明 32B 被要求时能做到，说明是**规格没把'唯一目标/逐约束核对'写进来**。
2. **`supported` 判定完全依赖 model 的数值推理，无确定性复算兜底** → 喂子机制 B（算术错）。`_Local32BVerifier` 对需算的题，把除法/求和/舍入全押给 32B，`gaps` 判空即支持，没有『数值必须可逐字符核验』的约束。

**与 api12 对照**：同一 spec，api12 无这类释放。两因叠加——(i) api 强策略产出的候选本就接近对（错候选少）；(ii) api verifier（更强的 lm）做身份消歧与数值推导更可靠。本地 32B 策略+verifier 的双弱在这里齐发：**策略给错候选，verifier 既不做逐约束消歧也不会复算算术**。

## 六、治本点

1. **VERIFY_INSTRUCTION 加"唯一目标 + 逐约束消歧"约束**（直接治 A）：
   `supported` 除"证据点名实体"外，还须——(i) 该实体是题干**全部约束**连乘下的候选；(ii) 对每个约束做身份/数值核对，任一矛盾即 needs_revision；(iii) 若证据里出现多个近似候选（如多部情景喜剧/多篇致谢第三人），必须指出并判不充分。32B 实测在收到这条后能正确消歧。
2. **数值答案确定性复算兜底**（直接治 B）：当答案或证据含数值，校验器返回前对关键数值做【法拉第式复算】——即由确定性代码（或第二次独立推导）重新算，且 `gaps` 不得在算术未核验时空。这层与模型无关。
3. **判分粒度修正**（伪影）：对数值/单位归一化（`cm=centimetres`、四舍五入容差），避免把本质对的答案判错，也避免 380/1139 混进 bad case。
4. **策略侧（呼应第一类）**：策略产出"部分匹配但非唯一解"的候选时，guidance 应提示先核对题干全部约束再 verify，别急着把一个表面候选拿去校验。

## 七、一句话总结（供报告引用）

> 32B 下第三类"实体/数值错"不是单一根因：约 9–11 例是 **verifier 对'表面/部分匹配'放行**（`VERIFY_INSTRUCTION` 只要求证据点名所述实体，没要求"题干全部约束下唯一目标 + 逐约束身份消歧"，32B 实测被告知后能消歧），约 2 例是 **verifier 自算算术出错且无确定性复算兜底**（624=66% 实为 65.53%、778=22 实为 21），另有 2 例是判分粒度伪影。同样是 **ESR 方案规格软×32B 弱校验的组合**，强策略（api12）下得以规避。治本在把"唯一目标 + 逐约束核对 + 数值复算"写进校验规格，便能同时堵住 A/B。

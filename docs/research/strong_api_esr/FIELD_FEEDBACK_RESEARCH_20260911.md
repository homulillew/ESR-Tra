# ESR 审核报告字段反馈：研究与实测（2026-09-11）

字段反馈候选在三个固定失败前缀上得到 **2/3 份合法否定报告，对照为 1/3**，但时间范围案例仍失败，未达到预登记的 3/3 门槛。数量案例还存在局部结论与理由不一致。因此保留候选为显式开启的实验选项，不改变默认配置，不启动完整开发批次，也不宣称答题准确率、成本或速度目标已达成。

本轮完成论文检索、失败轨迹分析、一个最小机制的实现、本地回归、真实同模型对照和账目复核。新增 **6 次 API 请求**，全为审核修复；没有 policy、judge、检索后端调用。累计 **1,404 / 2,000**，总剩余 **596**，当前检查点已用完。历史 13 笔未知用量继续占账，本轮没有新增未知用量。

## 当前方案与问题位置

ESR（Evidence-State Research，保存原始证据并维护当前结论和待解决问题的方法）由策略维护当前答案、目标和带证据引用的 claims。策略通过已有 search/open/read 工具获得原始观察，通过状态更新动作提交自己的结论。`verify_answer` 将原题、实际候选答案和允许引用的证据交给独立上下文中的远程审核模型。模型分别判断 target、coverage 和各 claim，程序校验报告结构、引用范围、原文一致性及 status/need 规则，合法报告才交回策略。E-soft 允许策略在收到合法的否定报告后自行决定后续动作。

这里存在三层不同要求：报告可被程序接受；报告正确发现题目与答案之间的缺失；策略看到报告后实际修正并正式提交正确答案。本轮仅检验第一层和整体否定信号，未测量最后一层。

三个既有失败前缀支持本轮优先级：合成数量题、合成时间范围题、开发题 790 都有明确的 status/need 冲突，笼统的一次修复反馈未解决。原始错误报告与证据已保存，因此无需再次调用模型生成初始失败。它们属于定向诊断，不能当成未见过的评测题。

## 最新论文如何影响设计

检索日期为 2026-09-11，以下均核对了论文原文；属于近期预印本，不把作者实验结果当成本项目效果。

| 论文 | 可用于当前问题的做法 | 本轮采用与限制 |

| [Closed-Loop Validation-Repair for Healthcare Interoperability](https://arxiv.org/html/2607.24371v1)，2026-07 | 修复输入包含原始任务、错误输出、schema 和具体字段错误 | 使用字段位置及现有规则，仍只修复一次。该论文主要验证结构合规，不能推出语义正确；不采用其领域规则 |
| [CAFE: Self-Improving Search Agents Need Co-Evolving Feedback](https://arxiv.org/html/2608.24794v1)，2026-08 | CAFE（Coupled Agent–Feedback Evolution，联合训练搜索策略和反馈生成能力）比较请求反馈后的收益，并用匹配轨迹训练反馈 | 借鉴“反馈是否改变最终结果需要单独测量”；本轮没有训练、额外反馈模型或运行时参考答案 |
| [Reviewer Capability Governs Rejection Targeting, Not Repair Skill](https://arxiv.org/html/2609.04270v1)，2026-09 | 固定初始答案，区分发现错误、改正、误改和未采纳 | 固定初始错误报告，只改变最后一条修复反馈。该论文将无法解析的审核视为接受、删除部分答案格式指令的做法不适用于这里 |

这些研究支持一次小规模字段反馈消融，而非证明“更多审核一定更好”。字段校验反馈已有研究先例，本轮不将它包装成新的研究算法。

## 实现与固定条件

在线版本为 `00ce56a`，分支 `research/strong-api-esr-20260909`。方案在 [实验登记](FIELD_FEEDBACK_PREREG_20260911.md) 中于调用前固定。

`validate_report` 收集所有 status/need 冲突，返回例如 `audit.target.need` 和 `audit.claims[0].need` 的位置、关联 status 字段及原规则。`repair_feedback=field_paths` 把这些信息附加到原有修复反馈；`generic` 保持原提示。接受规则、一次修复上限和完整报告要求相同。代码不修改模型的判定、答案或原始证据。其他错误类型保持原反馈。

审核模型请求为 EB-GLM-5.2，六个原始响应均为 `glm-5.2`；temperature=0.6，max_tokens=4096。网关别名无法固定底层权重版本。引用方式为 source_spans，完整原文被分段提供，模型选择的片段展开成原文引用。每份新修复最多一次真实请求，初始错误输出按历史记录回放并明确记为零新增生成。

数量和时间前缀保持原始 atomic 提示；790 前缀使用 task_first_literal：答案原样放在不冲突的标记之间，其他输入以 JSON 呈现。这只是恢复各自历史输入，**同一前缀的两组完全相同**。未把三个前缀视为同一种初始提示的自然样本。默认配置仍为 atomic/generic。

复核了实际发送的 provider body：每一对请求除最后的修复反馈外完全一致，generic 请求也与历史修复请求逐字段一致。原题、错误输出、证据、schema、采样设置均相同。历史初始生成的成本仍在原账本，不重复计入本轮的六次请求，也不将回放称为免费完成整道题。

## 逐例结果与原因

| 固定失败前缀 | generic：一次修复 | field_paths：一次修复 | 结论 |
|---|---|---|---|
| 数量约束：要求两项，答案只有一项 | target 和 claim 判 contradicted，却均未填 need，报告被拒绝 | claim 改为 contradicted 并给出缺失要求，报告合法 | 新反馈有局部作用，但 target 仍 supported，理由却承认只有一项，局部语义仍不可靠 |
| 时间范围：答案实体任期不覆盖所问年份 | target、claim 均 contradicted，need 均为空 | 明确收到两个字段路径后仍输出空 need | 定位信息不足以保证模型遵守跨字段规则；本轮机制未解决该例 |
| 开发题 790：候选缺少题目要求的字面引号 | target 改为 contradicted，coverage 保持 contradicted，报告合法 | target 保持 supported 并清空 need，coverage 保持 contradicted 且指明缺少引号，报告合法 | 两组均保留格式缺失信号，本轮不能把该例成功归因于字段反馈 |

合法且整体否定的修复数为 1/3 对 2/3，只有一对结果不同。没有出现合法且整体 supported 的误放行，但这不证明局部状态都正确，也没有估计对正确答案的误拒绝率。三个选定的失败前缀、每条件一次采样不足以支持稳定提升或显著性结论。

时间例的原始证据已足以否定候选，模型在理由中也正确指出任期关系；它仍把 `need` 留空。已确认的是“反馈明确、证据齐全、结构仍不合法”。一个待验证的解释是：模型把 need 理解成“还缺什么证据”，而契约同时要求在明确矛盾时描述“尚未满足的条件或需要如何改正”。这两种含义可能混淆。该解释不能仅由输出证明，本轮没有再改提示或放宽规则后重试。

数量例说明另一限制：确定性字段检查不能验证 reason 是否真正支持 status。即使程序成功交付报告，错误的局部判断也可能继续影响策略。更严格的协议修复和更准确的语义审核是两个问题，不能只统计 JSON 合法率来选最终 ESR。

## 无显卡的实际运行方式

本机 CPU 运行 Python 调度、SQLite FTS5 BM25 检索、证据读取、状态更新和日志；policy/auditor 由远程 API 推理。本地无需加载模型权重或使用 CUDA。已在这台约 8 GiB 内存、4 个逻辑处理器的电脑上实际运行多轮 BC+ 检索。

| 对象 | 实际配置 |
|---|---|
| 数据 | `D:/AgentSearchAssets/BrowseComp-Plus`，830 道题，100,195 篇语料 |
| 完整索引 | `indexes/esr-sqlite-bm25-20260909.sqlite`，4,393,078,784 字节，约 4.09 GiB |
| 检索 | SQLite 3.50.4，FTS5 `porter unicode61`，BM25 k1=1.2、b=0.75；字面词项 OR 查询，docid 打破同分 |
| 服务方式 | 进程内检索，无需端口 8000；三臂共享相同索引与工具能力 |
| API | Anthropic Messages 兼容协议，实际 POST `http://lanz.hikvision.com/v3/anthropic/model/v1/messages` |
| 模型 | 请求 `EB-GLM-5.2`；998 份已结算响应均返回 `glm-5.2`，底层权重版本未固定 |
| 采样 | policy/auditor temperature=0.6，单次 max_tokens=4096；judge temperature=0、max_tokens=1024 |

这是新建的 SQLite BM25 索引，与官方项目可使用的 Lucene 或稠密检索配置有区别；不能将其结果直接归为其他检索器的成绩。实现和重建命令见 [CPU_RUNBOOK.md](CPU_RUNBOOK.md)。[BC+ 官方实现](https://github.com/texttron/BrowseComp-Plus)和 [SQLite FTS5 文档](https://www.sqlite.org/fts5.html)用于核对数据与检索机制。

语料 SHA256 为 `086f1914ef7bcf0b9674e5ea435d3e23b5c552159916cba433ebb6fac5a5d39a`；完整索引实际读取后计算的 SHA256 为 `57dbceac110635126bc04422e2305bbada4f162302b7bb1da6d2048b52886201`。每局记录该指纹并检查路径、大小与修改时间，不宣称每局重新哈希全部索引。

## 必须更正的历史解释：请求 schema 的 ID 别名污染

`protocol.py` 的多个字段复用同一个 ID schema 字典。深拷贝整个工具列表仍保留内部别名；随后给 `read_evidence.observation_id` 添加动态枚举时，也意外限制了 `docid`、`focus.claim_id` 等字段。auditor 中也出现了 claim ID 枚举污染 observation ID 的情况。实际发给 provider 的约束因此与运行时验证不一致。

离线检查 1,001 份已导出的请求，**442 份受影响**，分布在 49 个目录。受影响的完整 rollout 为历史回归 3 局、pilot 25 局、开发 18 局；其余目录属于固定前缀诊断。每个目录新增 `schema_contract_warning.json`，原始请求、manifest、轨迹和判分没有改写。比较脚本拒绝把这些队列认证为合格的最终比较，不能只删除其中失败局后计算收益。

修复采用只替换目标属性字典的方式，解除别名，再施加属于该字段的枚举。保存状态的离线回放证明真实 docid 与 c0 现在合法，read_evidence 仍限于允许的观察 ID，基础 schema 保持不变。

此前文本诊断把模型输出的 c0 描述为无效 claim ID，这一归因错误：当时展示的枚举被污染，c0 本身合法。原诊断保留并添加 `schema_diagnostic_correction.json`。这一错误也削弱了 pilot 难度校准的有效性。多工具输出、额外 JSON 括号和引文抄写错误仍有独立原始证据，不能把所有失败都归给 ID 别名。

## 轨迹支持的最小迭代

完整决策和研究来源见 [DECISIONS.md](DECISIONS.md) 与 [RESEARCH_NOTES.md](RESEARCH_NOTES.md)。四轮主要改动预算已登记用完，不继续增加接口探针或轮换格式寻找幸运输出。

- baseline 重复正文与搜索后容量溢出：已用真实前缀离线定位，删除重复表示并补齐提交前检查；旧失败保留，不能称所有旧局已恢复。
- 原生多工具输出：固定前缀的 dispatcher 方案三次仅一次通过，拒绝启用。文本接口诊断没有稳定延续到完整 rollout，亦已回退；前述 c0 诊断归因另行更正。
- 引文与审核循环：旧 E-soft 可反复生成非连续引文或错归观察 ID。更精确的错误反馈没有稳定消除该问题。最后的最小机制让 auditor 从全部允许原文的确定片段中选 ID，程序还原对应原文，再执行原有范围、逐字匹配和 verdict 检查，不提升审核结论。

片段最多 1,200 字符，覆盖全部允许原文，不按答案筛选；原始模型报告、片段选择与展开报告均记录。其预测是减少引文复制错误和修复调用，代价是片段标签及较长展开引文可能增加输入。它受引用位置表达方式启发，**没有调用 Claude 专有 citations 功能，也不宣称 GLM 支持该功能**。[官方引用文档](https://platform.claude.com/docs/en/build-with-claude/citations)只用于研究实现思路。

片段模式尚无真实 API auditor 调用；仅合成测试通过。合法片段指针不等于证据蕴含，更不等于答案正确。下一项可证伪工作是使用已修复共同 schema 的固定开发队列，测量协议错误、审核调用及正式正确率；不再先增加新的机制。AgentFold 的训练与上下文管理、ToolMaze 对恢复和任务成功的区分也仅作为方法分析，未把论文收益移植为本项目结论。[AgentFold 原文](https://arxiv.org/html/2510.24699v1)、[ToolMaze 原文](https://arxiv.org/html/2606.05806v1)。

## 剩余限制

目前结论属于“服务与有效数据不足，不能判断”。共同工程契约的离线可靠性得到加强，旧 API 基本链路确实运行过；最终 ESR 机制效果尚未得到真实验证。除配额与不完整队列外，还包括难度分层不可靠、网关模型版本无法独立固定、thinking 默认值未验证、计数接口不可用、窗口采用保守 UTF-8 字节估计而非远端 tokenizer、同模型 judge 的相关误差、一个保留原分的判分争议，以及缺少可靠价格。

数据隔离通过 questions-only 输入、独立评价进程和执行阶段实现，现有 Windows ACL 仍为继承权限，没有独立安全账户。暂停统计对不同的不可解析输出可能产生相同通用错误签名，不能因此认定是同一个提案。上述限制均保留，不用合成测试、HTTP 200、正确草稿或 supported 审核代替正式正确提交。

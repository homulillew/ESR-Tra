## 当前方法与需要分别验证的环节

ESR（Evidence-State Research，保存原始证据并维护当前结论和待解决问题的方法）把原始观察与策略写入的结论分开保存。策略使用检索和阅读工具取得证据，再更新候选答案、待满足要求、带原文引用的事实与当前问题。`verify_answer` 在独立上下文中调用远程审核模型，检查答案目标、要求覆盖和各条事实。程序校验报告结构、引用范围、原文对应及状态字段的一致性，合法报告交回策略；策略决定修改、继续查证或提交。

本轮在线 policy 和 auditor 均为用户指定的 **EB-GLM-5.2**，27 份响应的模型标识均为 `glm-5.2`。Codex 负责离线研究和执行，没有代替在线模型给出自然题目的动作或审核结论。网关别名未固定底层权重，不能保证重跑得到相同输出。

需要区分四个结果：

1. **工具与状态正确执行。** API 返回的完整参数有没有被执行，成功动作是否提交，每项调用是否有回执。
2. **审核报告合法。** 返回结构、引用和 `status/need` 是否满足契约。
3. **审核判断正确。** 能否发现真实缺失，同时接受已经正确的答案。
4. **策略真正修正并提交。** 收到反馈后，完整动作是否改变错误答案，最终提交是否正确。

这四项不能互相替代。合法报告可能误判；正确反馈也可能只增加调用，没有转化成正确提交。审核模式为 E-soft：合法的否定审核不会禁止策略提交，但实际否定状态保留。它属于 ESR 内部配置，不是无 ESR baseline。

## 机制一：说明状态与 need 的合法组合

调用前登记见 [ADMISSIBLE_REPAIR_PREREG_20260911.md](ADMISSIBLE_REPAIR_PREREG_20260911.md)，在线代码为 `5e49981`。

两个独立历史失败前缀中，模型已经给出否定结论，却保留空 `need`。尤其在证据已足以证明矛盾时，“还缺什么证据”与“需要改正什么”容易混淆。这是待检验解释，不能仅凭输出证明模型的内部原因。

`repair_feedback=admissible` 只在状态与 `need` 冲突触发修复时，说明三种合法组合：`supported` 要求空 `need`；`unknown` 说明缺失前提；`contradicted` 说明违反的要求或必要改正，即使无需增加证据也必须填写。程序没有替模型选择状态、填字段或改答案。初始请求、报告 schema、引用规则和一次修复上限保持不变。

| 固定初始失败 | 字段路径对照：一次修复 | 明确规则候选：一次修复 |
|---|---|---|
| 数量：要求两项，候选只有一项 | 合法否定 | 合法否定；target 仍支持，局部语义不完全一致 |
| 时间：候选任期不覆盖所问年份 | 否定状态仍配空 need，报告不合法 | 合法否定，并给出必要改正 |

每对实际 provider 请求只改变最后的修复消息，初始失败响应取自已经计费的原记录，未再生成。合法否定报告为 **1/2 对 2/2**；候选两次修复用 3,281 输入、780 输出 token，对照为 2,875 输入、680 输出 token。样本只有两个指定失败前缀，不支持稳定性或统计显著性结论。

通过前缀检查后，候选做了四次新审核：数量和时间正例正确支持；已带引号的合成正例被误拒绝；真实开发题 790 的原始未带引号候选被错误支持。两处字符误判均发生在首个结构合法报告，**没有触发新修复反馈**，不能归因于修复规则，也无法被只在报错后生效的机制纠正。

因此本阶段在 8 次请求后停止；完整合成策略任务与九题三条件的 27 局自然开发调度均未执行。决定为：**保留实验选项；有限的协议修复收益成立，自然任务收益未测量。**

## 机制二：给审核模型精确的答案字符属性

调用前登记见 [ANSWER_SURFACE_PREREG_20260911.md](ANSWER_SURFACE_PREREG_20260911.md)，在线代码为 `9f33d1a`。

两份首轮请求已经完整提供答案字面字符，审核却把存在的引号说成不存在、把不存在的引号说成存在。本阶段新增 `profile=task_first_literal_surface`：在原样答案之外提供 Unicode code point 长度、首尾 code point、ASCII 双引号 U+0022 的数量和首尾位置。属性只由 `answer` 计算，不读取题号、题意、参考答案或历史判分，也不自行判断题目是否要求引号。两组都使用相同的 `admissible` 修复规则。

三对初始 provider 请求已逐字段核对：仅增加字符属性及固定解释，原题、证据、候选答案和 schema 相同。

| 审核包 | 字面展示对照 | 字符属性候选 | 实际请求数：对照／候选 |
|---|---|---|---:|

字符审核包通过预登记门槛，随后启动一次完整合成策略任务。**这只能证明此次包级检验通过，不能证明策略完成了修正。**

## 完整轨迹：反馈已送达，三次更新没有改变答案

合成 Orin 任务要求返回首任负责人，并在姓名两侧保留字面双引号。证据来自本地合成检索器，不是 BC+ 题库或外部检索服务。单局最多 8 次远程请求，包括策略和审核。

| 顺序 | 远程调用与动作 | 实际状态或回执 |
|---|---|---|
| 1 | 策略调用 search | 找到合成来源 |
| 2 | 策略调用 open_page | 原文完整交付，获得 o1 |
| 3 | 策略调用 update_state | 写入正确姓名及原文引用，但答案没有字面引号 |
| 4–5 | 策略调用 verify_answer，触发一次审核请求 | 合法否定；target、coverage 均指出缺引号，字符计数为零 |
| 6 | 策略调用 update_state | 参数仍为原姓名；`noop=true`，状态版本不变 |
| 7 | 策略文字说明要加引号，又调用 update_state | 实际工具参数仍为原姓名；`noop=true` |
| 8 | 策略再次说明要加引号并调用 update_state | 实际工具参数仍未变化；`noop=true`，随后请求上限终止 |

复核得到：

- 7 项原生工具调用都有对应回执，零丢弃、零工具执行错误。本例没有多工具同轮输出，不能据此扩大为所有多工具情形都无 bug。
- 三个后续策略请求都包含当前否定审核；target 和 coverage 的具体 need 与原报告完全相同。部分 reason 在状态视图中缩短，但要求加引号的 need 完整，策略文字也明确提到这个要求。
- 原始 API 响应中的答案参数、实际执行参数和提交后的状态逐一相同；程序没有删掉模型返回的引号。回放所得最终状态与 summary 一致。
- 三次 `noop` 正确保留原状态版本和当前审核，没有把“调用了更新工具”虚报成答案已经修正。
- 最终为 `request_budget_exhausted`，正式提交为空，保留未修正草稿；耗时 **35.88 秒**，计失败，正确完成时间无值。没有因为人物事实正确就算成功。

这把当前断点进一步定位到**远程策略返回的修正动作没有落实反馈**。无法仅凭网关外部记录区分底层模型生成与上游格式转换各自的作用；它们都早于本地工具执行。审核输入增加字符属性，也没有改变策略输入的答案展示方式。只提高审核准确性，仍可能得到重复无效动作和更高成本。

请求上限也是本次条件：审核后只剩三次请求。系统允许有序组合动作，因此可以组合更新和复核以节省请求，但不能假定策略会这样做。本轮没有与 16 次请求条件比较，也未延长失败局；不能声称已证明增加预算有效或无效。

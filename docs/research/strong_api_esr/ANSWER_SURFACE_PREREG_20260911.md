# 答案字符属性实验登记（2026-09-11）

这是本次继续研究中的第二个独立机制。前一阶段 `ADMISSIBLE_REPAIR_20260911` 用 8 次请求完成：明确修复规则使数量和时间两个前缀均得到合法否定报告（对照 1/2），但首次审核误拒绝已带引号的合成正例，又错误支持未带引号的 790 候选。两次错误都没有触发协议修复，不能归因于新修复反馈。前一阶段按原门槛停止，记录不改写。

## 假设与机制

**观察：** 两份实际 provider 请求均完整包含答案字面字符，模型却分别声称存在的引号不存在、不存在的引号存在。问题位于审核对答案字符的判断，不是工具丢弃、原文未交付或程序剥去引号。

**假设：** 在审核输入中提供由程序从当前答案机械计算的字符属性，可减少模型对引号的感知错误，同时保持题意判断由远程模型负责。

**唯一新机制：** `profile=task_first_literal_surface` 在原样答案和完整原题、证据之外，提供长度（Unicode code point 数）、首尾 code point、ASCII 双引号数量及是否位于首尾。这些属性只依赖 `answer`，不读取 question/qid、参考答案或历史正确性标签。所有题使用同一函数。它不判断是否应加引号，不生成答案、不修剪空格、不修改状态、不自动支持/拒绝。ASCII 属性明确指 U+0022；Unicode 引号只由首尾 code point 反映，不声称两者相同。

程序附一段固定说明：属性是当前字符串的事实，不是合规标签；模型只能执行原题中的约束，不能因出现引号属性就要求所有答案加引号。其余 initial prompt、报告 schema、接受规则、引用、工具和状态机制不变。两种审核配置都使用已完成条件检验的 `repair_feedback=admissible`，把修复反馈作为共同条件。

**代价：** 每次审核增加固定大小的属性和说明，可能诱导过度关注引号，也可能被模型忽略。因此同步比较有引号和无引号两种候选，并用单位正反例检查是否错误地推广引号要求。

**证伪：** 候选误拒绝正例、误放行负例、不能正确识别真实 790 包，或没有任何同步对照差异，均不启动自然开发集。不得只保留有利题目、换门槛或自动替模型改判。

## 研究依据

[CharBench: Evaluating the Role of Tokenization in Character-Level Tasks](https://ojs.aaai.org/index.php/AAAI/article/view/40615)（AAAI 2026，2026-03-14）说明字符计数和位置判断仍是模型困难项，但词长、计数与分词特征的影响不同，不能将所有字符错误直接归因于 tokenizer。本文据此把机械字符属性与语义判断分开测试，不把 benchmark 的发现当成本项目根因证明。

[Spelling-out is not Straightforward](https://arxiv.org/html/2506.10641v1)（2025）通过约 7B 模型的字符预测与内部探测，区分完整拼写和单字符判断能力。它不测试本项目的 GLM、引号验证或外部属性辅助；本轮不移植其训练与神经元分析，也不声称修改了远程 tokenizer。已有 [VeriHarness 修复实验](https://arxiv.org/html/2607.14167v1) 的范围检查同样提示：未被校验器暴露的语义错误，无法靠修复消息解决。

本机制是确定性字符属性辅助审核的工程消融，不主张新算法或新的训练奖励。

## 固定预算与调度

开始累计 **1,412/2,000**，已登记 **157** 个单位，非确认阶段还剩 **29**；不得占用 54 个确认名额。当前九题均为重复使用的开发题，不能作为泛化证据。

1. 固定 quoting-positive、quoting-negative、790 原始 packet，在 task_first_literal 与 task_first_literal_surface 下各一次新审核（各最多 2 请求），顺序按 packet 交错。共 6 个单位、最多 12 次请求。两组都从新审核开始，不给初始错误报告，不额外重采样。原题、候选、证据和 schema 相同；变化仅为字符属性及解释。
2. 候选再审核 unit-positive、unit-negative，各最多 2 请求，共 2 个单位、最多 4 次请求。候选五份 packet 必须均合法：两个正例 supported、三个负例 unknown/contradicted，790 的具体 need 须指出引号缺失；三对同步比较至少一例优于对照。通过后运行一次完整 Orin 合成策略 episode，最多 8 请求，要求提交答案与合成证据及字面引号要求一致、所有调用有回执、无审核协议错误。
3. 全部通过后，在固定九题 149、790、26、785、301、1012、701、1044、718 上运行 **两个 E-soft 条件各一次**，逐题交错顺序：literal/admissible 与 literal_surface/admissible。共 18 局，每局最多 16 次在线请求，在线全部结束后每个正式答案最多 1 次独立判分，最多 306 次请求。

总上限 **27 个新增单位、330 次新增请求**。保留完整九题，以两种有审核的 ESR 条件隔离本机制；episode 余额不足以同时做上述机制检查和九题三条件的 27 局自然批次，因此本阶段不新增 E-off。用户暂停无 ESR baseline 的要求仍生效。本阶段不产生 ESR-vs-B 或 ESR-vs-E-off 的新性能结论，确认集不打开。

模型仍为 EB-GLM-5.2，预期响应 glm-5.2；temperature=0.6、max_tokens=4096、一次协议修复、完整 CPU 检索索引、状态与工具配置均保持。分阶段提高预算检查点，总额不变。

## 分析和停止

分别记录：原始字符串属性是否正确、报告是否合法、审核是否误拒绝/误放行、错误是否真实传给策略、策略是否改答案、最终提交判分、全部 model/tool 成本及耗时。正确报告不能替代正式提交正确率。

基础设施、未知用量、实际模型变更、schema 或回执异常即暂停；候选连续两局审核协议失败则停止余下调度。所有失败、剩余未执行清单与原始记录保留。缺失或预算终止按失败计，不扩局，不通过重跑获得幸运成功。自然批次启动后冻结代码；若本机制也未通过门槛，本次继续研究以两个机制的真实结果收束，不开启第三种机制。

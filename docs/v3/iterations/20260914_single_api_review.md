## 1. 传输完整性通过本次检查，语义正确性仍需另查

本地将每轮实际 HTTP 请求体与 harness 的 wire_request、messages/tools/max_tokens 逐项对照；将响应体与 policy_response.raw 对照；将原生工具 ID、顺序、数量与 action_attempt 对照；将成功提交参数与原生参数对照；将回执与紧接着的下一轮同 ID 工具消息全文对照。全部通过。

12 个响应各含两个工具调用，没有只执行第一项或静默丢失后续项。41 项调用都得到本地回执，其中 40 项需要再发给模型，均完整送达；最终提交后的回执只存本地，未为了回传它再发起收费请求。

这可以排除本次运行中的上述丢失问题，无法证明所有 provider 响应形式、错误分支或模型行为均正确。第 16 轮使用了已发布的有效文档编号，却选错目标对象，属于语义选择错误；已有 ID 映射检查不能判断策略阅读意图。

审阅时不要建议按模型自由文本猜测并改写 ref，那会改变被测策略的实际动作。可以检查标题、来源和编号的显示是否足够邻近、清楚，再单独验证其影响。

## 2. 工具描述没有说明实际检索语义

`protocol.py` 的 search 描述是搜索语料；采集脚本的 LocalIndex 实际执行小写化、正则提词、去重、词间 OR，再交给 FTS5。引号和 site 不具有用户通常期待的网页搜索功能。

模型多次使用这两种写法，可能以为不断缩小查询，后端却按多个词任一命中处理。传输层保留了完整参数，检索适配器改变了参数的解释。这是工具能力约定与真实后端不一致，不能归因于 API 截断 JSON。

后验只读 SQL 检查显示：目标人名的连续短语匹配 0 篇，两词 AND 匹配 8 篇，抽查中包含不同人物姓名分处一文的情况。不能由此断言全部变体或语料绝无证据，但也不能把重复 OR 查询等同于有效核验。

下一项最小假设：只明确描述本地语料范围、不支持 site/短语及 OR 规则，在模型、题目、索引、排名和预算固定时，能否减少未补齐证据的重复查询。需要报告正式任务结果，不能只报告调用减少。本分支未更改工具描述或运行该对照。

进一步审阅问题：检索能力声明应由具体 retriever 提供，还是写入所有后端共用的全局提示？本次发现只证明 LocalIndex 的行为，不应把它误写成所有检索后端的限制。

## 3. 上下文压缩与持久结论的保存时机不协调

第 6 轮已经获得原刊 o1，第 10 轮压缩后 o1 仍可见。第 16 轮读错页使 this 转为 o2，第 18 轮压缩后仅 o2 可见，候选名称在实际请求中消失。此时策略没有保存任何持久结论；直到第 28 轮才新增 c1/c2。

第 19 轮出现猜测词，第 20 轮重新打开关键原刊。这与关键正文退出当前输入的时间吻合，但因果关系尚未通过固定前缀对照确认。原文仍在账本中可恢复，不等于当时模型正在看到它。this 表示当前明确绑定的原文，也不承诺保留全局最重要的原文。

设计上的待检验问题是：模型自行选择何时保存结论，而 harness 自行决定何时裁剪历史。如果策略不知道哪些已读内容即将退出输入，就可能过晚保存。字节上限也不等于强模型实际 token 窗口，不能把这次裁剪行为直接归因于模型上下文能力。

审阅应检查 context.render、history 的 observations/claims/documents、this_candidate 的变化和持久结论呈现方式。区分提醒策略保存、保留用户可核查的原文、扩大上下文预算三种改动；一次只检验一种。不要为了保证有状态而要求每页写一条结论。

## 4. 已修复的 executed 标记错误及其边界

第 25 轮输入包含 cursor 与 query。schema 规定 cursor 续读不能同时携带 query，校验在 `_dispatch` 前失败，旧版 ContractError 分支却统一写 executed=true。下一轮模型收到错误后正确删除 query，表明参数错误能够恢复。

本分支唯一核心修复为：分发前 dispatched=false；进入 `_dispatch` 前置 true；拒绝回执使用该标记。它使 executed 表示进入工具分发，不能拿它统计外部调用或成功状态提交；分别需要 backend_request 和 action_commit。

合成测试覆盖校验失败后未执行后端、后续工具 not_executed、所有回执进入下一轮，以及已进入分发后失败的反向场景。修复前反例失败，修复后联合回归 275 通过。未新增真实调用，不宣称减少了实际搜索或提高了准确率。

审阅者应检查这个字段是否仍有误读风险，以及使用方是否错误地把 executed 当作后端成本。若需要改变字段契约，应另列最小改动与兼容性检查，不把已通过的离线修复说成全链路完成。

## 5. 引用有合法来源，复合结论仍可能缺少支持

第 20 轮送达的 o3:p2 包含主要名称及所有者，o3:p3 包含地点细节、DJ 和音响价格。第 28 轮 c1 合并这些断言，却只引用 p2。不是原文未送达，而是最终选择的来源范围较窄。

c2 的金额引用同样跨越边界：出售主体和年份在 o6:p4，金额在 p5。固定 700 字符切分把一句话拆开，最终只选 p5，缺少主体和时间信息。不能自动补齐相邻引用后声称模型本来就引用完整。

require_sources 检查真实来源路径，不保证每个断言得到语义支持；本次 auditor 可选且未调用，因此 submitted/unverified 只表示已提交未审核。候选名称在原刊中有依据，但完整线索仍有未独立证实的内容，未作正式判分。

后续应分别审查文本切分、findings 复合断言与 refs 的对应、audit 接收到的实际答案包。审核如果读到额外相邻原文，应明确它是在原引用范围内判定，还是在扩展证据后重新核验，不能混成同一种指标。

## 6. 对 ESR 方案能得出什么结论

本次只有一次 update_state，且在倒数第二轮；verify_answer 为 0。因而可以诊断工具和状态接口，却不足以证明持续保存结论、修订依赖和审核反馈组成的完整方法有效或无效。也不能把这道题与历史不同配置 baseline 直接拼接成比较。

已观察到的实际过程是：找到关键证据、持续追查辅助线索、读取错页、关键原文退出输入、重新阅读、最后保存结论并提交。下一步最有价值的是针对其中一个明确环节建立最小反例和固定条件对照，而非同时加入记忆、查询重写、强制审核等机制。

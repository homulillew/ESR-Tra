# Harness 查询门控（query gate）的合规三态与取舍原则

日期：2026-09-02
关联：[RL_PRECHECK_HARNESS_LEGALITY.md](RL_PRECHECK_HARNESS_LEGALITY.md)（RL 前 harness 介入合规总体梳理）
前置：本文是对"RL 前整改"中一个更细、更深的问题的专项分析——harness 是否应当对模型的检索词（query）做合理性判断，并对不合理的检索词"返回重发"。

---

## 一、问题界定：三类 harness 介入的本质区别

针对"模型给出的动作"这一对象，harness 的介入有三类本质不同的机制，合法度天差地别：

| 类型 | 机制 | 状态机角色 |
|---|---|---|
| **① 引导（提示）** | 把建议写成提示词，模型可选择接受或不接受 | 不改动动作空间，只影响采样倾向 |
| **② 拒绝（协议）** | 依据协议规则否定某个动作，要求模型另发 | 依据**协议不变量**（证据不可改、未登记不可更新等），不涉及答案对错 |
| **③ 门控（gate）** | 对模型动作先做"合理性"判断，不合理则**不进入执行，返回重发** | **改写了模型的可行动作集合**（action support）。模型对"被 gate 滤掉的动作"的采样概率**不进入 reward**，也不产生梯度 |

本文讨论的是第 ③ 类。它的特殊性在于：第 ③ 类不是提示也不是拒绝，而是**把模型的动作空间切开**——被滤掉的检索词从未真正执行。这正是提问者点出的"harness 缩小策略搜索范围"的感觉。

---

## 二、一个关键事实：我们当前没有 query gate

现状核对（`environment.py search()`）：当前对检索词的唯一校验是 `if not query.strip()`（拒绝空串）。其余全部属于提示层（guidance / `_gap_worklist`），**不存在"判断检索词是否合理、不合理则返回重发"的硬性门控**。

这一点很重要：我们对第 ③ 类的讨论不是针对已有代码，而是针对"是否应当新增这样的门控"。这决定了下文是原则判断而非代码审计。

---

## 三、核心洞察（先确认对的部分）

**"训练与部署保持同一套 harness，模型学到的是该 harness 约束下的合理行为，而非自身学会合理检索词"——这在一种前提下完全成立。**

若门控是**确定性、两端一致**的滤波器（filter）：
- RL 训练时，被滤掉的动作不计 reward、不产生梯度；
- 部署时套用同款门控，模型输出自然被滤成门控允许的子集；
- 只要训练、部署的门控完全相同，模型学到的策略就是在门控约束下的最优策略，部署行为一致，**不会崩**。

这在强化学习中对应"滤波器一致性 / 世界模型一致性"：只要滤波器是确定性的且两端相同，学得的策略就是在过滤后动作空间里的最优策略。**这条结论对第 3 种是成立的**。提问者的判断在此是对的。

---

## 四、隐藏陷阱：三种"合理性判断"依据，合法度完全不同

"harness 判断检索词合理"这个动作，按它**依据什么来判**，可拆成三种情形。真正的风险不在"是否做 gate"，而在"gate 依据什么"。

### 情形 3a：依据协议/格式判
例如：检索词非空、合法、长度在界内、确实是"检索词"而非计划文本。

- **完全合法**，且各阶段都应有。这是机械校验，不涉及模型能力，也不涉及检索器语义。
- 当前 `if not query.strip()` 属于这一类，只是太弱；可增强为长度界、非法 JSON 等纯格式约束。
- **是推荐保留、可适当加强的一类。**

### 情形 3b：依据检索语义相关性判
例如：用 BM25 / embedding 对检索词与文档做相似度，判断"这个检索词能否搜到相关内容"，不足则重发。

- **最危险的伪合理性**。它引入了一个独立于模型的**检索质量度量**做门控，本质是把"搜索好不好"的判断外包给外部检索器。
- 具体问题有二：

  1. **sim-to-real 在 3b 下不成立**：门控的通过标准依赖外部检索器（BM25 版本、embedder、文档库）。训练与部署之间一旦检索器漂移，门控的通过集合即变化，模型行为立即失配。所谓"同一套 harness"的前提在 3b 下不成立——因为 harness 依赖的是一个并不恒定的外部语义判断。
  2. **reward hacking**：模型很可能学会"凑出能让门控放行的检索词"作为捷径，而非真正提升检索质量。梯度被门控的通过与不通过主导，而非被任务奖励主导。

- **不建议做。**

### 情形 3c：依据是否匹配当前缺口（gap）判
例如：对比检索词与未解缺口的关键实体，判断检索词是否"对准了该解决的缺口"，不对准则重发。

- 介乎 3a 与 3b，但**最接近提问者担心的"缩小搜索范围"**。它不是判格式、也不是判检索质量，而是判**策略方向**——"当前检索词对不上该补的缺口"。
- 这正是 RL 想让学生学会的**收敛决策**（该补缺口时不要检索不相关的东西）。若门控滤掉这类检索词，等于替模型做了检索方向的元决策，与 `_gap_worklist` 是同一类决策泄露，只是形式从"提示"升级为"门控"——更隐蔽，且因为被滤掉的动作不进 reward，更难在训练中被发现。
- **不建议做。**

---

## 五、取舍原则与明确结论

1. **提问者的洞察，在"格式/协议门控（3a）"与"训练=部署同一门控"的前提下成立**：模型学到的是门控约束下最优策略，两端一致不崩。这一点对格式层完全成立。

2. **但对语义（3b）与策略（3c）门控，"同一套 harness"恰恰是脆弱的**：它们依赖外部检索器的语义判断与一个"合理性"标准，训练/部署间、不同检索器间会漂移。一旦漂移，sim-to-real 即破坏——而这比"帮模型改"更难察觉，因为训练时奖励仍正常（模型在门控放行的子集内表现好），问题暴露在部署时。

3. **可做与不可做**：
   - **可做**：3a 格式/协议门控——检索词非空、长度界、合法 JSON。这是滤波器，两端恒定、合法。
   - **不做**：3b 检索语义门控、3c 策略方向门控。它们留给"提示层"（模型可接受可不接受），或改写成冷启动 SFT 示范轨迹（教模型自己判断），不要做成硬门控。

**一句话总结**：harness 能做的是"在格式层切开动作空间"（filter，两端恒定、合法），而不是"在语义层切开动作空间"（策略注入，两端不恒定、会被 reward hacking）。前者是 harness 的正当职责，后者会挡住模型自身策略的学习。

## 六、对 RL 前整改清单的补充

| 新增动作 | 与现有整改的关系 |
|---|---|
| 保留并适度增强 3a（检索词格式门控），作为唯一允许的 query gate | 属类别 A（协议强制拒绝）的延伸 |
| 3b / 3c 一律不引入硬门控 | 与 R1（`_gap_worklist` 降级）同方向：检索方向决策交还模型 |
| 若需要"对齐缺口"的引导，只写在提示层，或作为 SFT 示范轨迹 | 与"降级强引导为 SFT 冷启动示范"一致 |

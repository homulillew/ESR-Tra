# Discovery-02：检索入口提示没有提高准确率

本轮在同一正式 STRIDE CLI、full 工作流、GLM 服务（实际响应 `glm-5.2`）、temperature=0 和只读 CPU FTS5 索引下，比较 `baseline` 与 `search-pivot-v1`。唯一变化是在连续两轮搜索未取得新原文时，向既有下一次请求加入一条换检索入口提示；每题最多两次，不增加专门模型调用，不改写查询。运行 SHA 为 `3f214db0a6854b1820ed97b5f06d1b06f7e9e83d`；完整配置与源码哈希见 PLAN.json。

**实际结果：基线 2/4，候选 2/4，净增益 0；配对胜 0、负 0，双侧精确配对检验 p=1。** 两道控制题无回退，q775、q774 仍未提交答案。该候选未通过开发筛选，不进入十二题复验，也不作为已证明有效的产品默认方案。

## 机制是否实际生效

q775 候选在 R3、R5，q774 候选在 R6、R8 各触发两次。档案事件与实际 HTTP 请求中的 control 字段完全一致，说明提示确实交付。但随后模型仍使用原候选或原奖项名称发起查询，没有换成独立线索。机制的执行检查通过，策略行为和任务结果的改善没有通过。

q775 候选在已有可读来源后仍延迟读取，后续窗口缺少明确主体前文，出现姓名拼接、出生地与成长地混淆；到 R16 才提出换线索，已处于 FINAL，search 被拒。基线在 R14 进入工作流的 FINAL 时仍有三次模型额度，工具只提供 finish，却继续搜索，终态为 stalled_no_submission。不能把这个基线失败解释成原模型调用额度耗尽。

q774 两臂都围绕一组真实亲属关系展开，但没有补齐角色婚姻次数、存活子女和身高要求，最后均弃答。候选臂较早读原文发生在首次提示之前，不能归因于机制。详见 Q775_AUDIT.md 与 Q774_AUDIT.md。

每题两臂首个请求逐字节相同，但部分首轮输出已经不同，体现实际服务在 temperature=0 下的运行差异。四个控制槽均未触发干预；其检索数和耗时差异不能作为该机制有效的证据。

## 正确答案与来源分别审阅

q778 两臂均显式返回 JSON 整数 21，经既有 `string-integer-v1` 规则表示为 terminal 字符串 "21"，引用 e1。两臂 e1 原文逐字节相同，含人物、母亲当时年龄及文内时间支持。原始整数、转换记录、文本终态与 refs 保持可追溯。

q771 两臂的 Vakkorama 名称和 1982 年青年品牌信息有直接原文支持。不过候选臂引用的窗口未明确说明与儿子共同创建；e2 仅能证明亲属关系，不能补出共同创建事实。该句在基线引用的另一窗口中，而候选臂没有读取该窗口。塔楼建造年代也未在两臂所引用窗口中完整核实。因此报告保留 judge 的答案判对，同时明确不是所有识别线索均已由本臂 refs 验证。详见 CONTROLS_AUDIT.md。

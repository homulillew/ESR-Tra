# 文档读取时机：支持与反例

本轮只改变一次请求的可用工具集合，让模型自行选择原生 read 动作。它既不自动取页，也不把导航摘要当作已读原文。行为门槛与结果准确率分别评估。

- [Fetch-then-Explore](https://arxiv.org/html/2608.02097v1)，2026-08-03。在固定搜索和 ReAct 外层下，35B 模型 BrowseComp 的 snippet-only、visit-snippet、完整方法分别为27.5%、30.5%、44.5%，说明页面交互接口会影响结果。但完整方法没有隔离“一次禁止 search”；其最多300轮、平均58.3次搜索加选择与抽取，远超本轮预算。35B 的 WideSearch Row-F1 为34.3，低于 visit-summary 的35.5；连续搜索也存在于成功轨迹。文中定位操作经常先于读取，因此本轮不提供 find 的一次请求也可能只读页头而错过关键段落。
- [Budget-Aware Tool-Use Enables Effective Agent Scaling](https://arxiv.org/html/2511.17006v1)，2025-11-21。论文区分候选探索和属性验证，指出过早验证可能耗费预算而没有进展。完整方法包含计划、核查、摘要、继续/转向及候选选择，没有提供 read-only 工具屏蔽的独立消融。[作者实现](https://github.com/google-research/budget-aware-agent)还涉及额外摘要模型；完整方法的增益不能归于本轮零额外请求的规则。

这些来源支持检验页面交付与预算分配，不能证明三轮搜索等于错误，也不能证明读取任意候选有益。已封存开发轨迹既有长期没有 read，也有读到局部事实后错误绑定主体。一次限制工具只针对前者；若模型不产生合法 read、读取范围无用或最终仍错，均应如实判为未达到目标。

强制 AND、稀有词截短或增加隔离检索分支也曾作为备选复核，但当前证据不支持将其与本轮叠加：它们分别改变执行查询或请求分配，会使一次工具限制的结果难以解释。本轮保持原 CPU 查询实现。

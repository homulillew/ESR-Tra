# 搜索附带有限原文的对照实验

## 问题与假设

研究目标是在相同模型请求上限下提高答案正确率，并分别核算工具、后端和 token 成本。当前完整工作流使用只读 CPU SQLite FTS5 检索、原生 search/read/find 工具、已交付来源授权和显式 finish。搜索摘要用于导航，只有实际交付的原文窗口可引用。真实运行中存在已经搜索到页面却没有主动读取的失败；另有读到原文后仍混淆人物、日期和关系的失败。

本轮假设是：在 search 回执中确定性附带少量真实原文，可减少一次主动 read 的依赖，使模型更早接触可核查内容。窗口的词面匹配不证明候选正确，也不验证题目关系。相关论文及其迁移限制见 [LITERATURE_SEARCH_RAW.md](LITERATURE_SEARCH_RAW.md)。

## 唯一协议变量

对照为 `baseline`，候选为正式 CLI 可选的 `--decision-protocol search-raw-window-v1`。两臂均从空 episode 开始，使用相同问题、模型服务和实际身份、temperature=0、full 工作流、`string-integer-v1`、CPU 索引、Config 和计量边界。实验名称、论文、分析、参考答案和人工候选不进入模型输入。

候选公开声明 search 的复合执行语义：

1. 原 search 校验、全部 query 检索及导航返回照常执行。整条 search 成功后，仅考虑第一个 query 排名第一的文档，不轮转、不选择后续 query 或其他命中。
2. 每条 episode 最多自动尝试六个不同文档。首 query 没命中、文档已尝试或六次耗尽时明确跳过。后端余额为零且没有缓存 snapshot 时跳过，不占自动尝试。开始前已到时间上限则按原时间合同终止，不占自动尝试；允许开始时在获取或使用 snapshot 前记入尝试，no-match、失败和之后的容量 withholding 均不退还。
3. 通过统一 `_snapshot` / `_backend` 读取原文。以第一个 query 的原始字符串调用既有 `paragraph-lexical-v1` 选择器，长度最多 `min(read_chars, 3000)` 个 Unicode 字符；本轮 read_chars=3000。无词面匹配时不生成窗口，不回退到页首，不把 snippet 转成原文。
4. 匹配窗口由 Archive 保存完整 snapshot、字符范围、原文和哈希。search 回执中的 `raw_windows` 明确标为 harness 自动取得，原 hits/snippets 保持导航身份。不伪造模型 read 调用、不自动提交答案。
5. 沿用完整回执的容量检查、固定 received-reference binding 和实际输入后的 delivery_ack。同一模型响应后续动作不能引用刚搜索取得但尚未交付的窗口。整条结果被 withheld 时窗口仍留档，但不授权、不回滚资源消耗。
6. 真实后台或文档完整性异常保存原搜索导航和部分执行记录后停止队列；不重试、不换提供方。600秒局部时间用尽按既有合同结束本槽，传输超时则停止队列。FINAL、动作上限、后端上限和终答规则不变。普通跳过或无匹配不自行结束 episode。

工具说明只替换旧说明中与新复合行为冲突的句子并追加本协议；其他 search 指导、参数 schema 和所有其他工具保持不变。SYSTEM 明确区分导航片段与自动取得的原文。规则、描述和说明各有哈希，源码与实际输入另行封存。旧协议可继续运行和回放。

一个 native search 仍计一个模型动作；自动获取是该复合动作内部的额外工作。每次实际 get_document 计入共享后端额度，缓存 snapshot 不冒记后端请求。报告另列自动尝试、成功窗口、实际交付、跳过、no-match 和 withheld，不能用 native read 数降低代替总成本降低。真实新窗口的交付可能改变既有 bounded recovery 状态，这也是机制效果的一部分。

## 本地验收与冻结

使用非研究题 synthetic fixture 验证：两种 provider 的实际 schema 保持一致；首项选择及无 fallback；六文档上限；Unicode 原文范围和哈希；no-match、snapshot 缓存及后端不足；容量 withholding 后不授权；部分后台失败与后续动作停止；FINAL；新原文和重复原文的交付进展；实际产品 CLI 经本地 HTTP、SQLite、只读 replay 和导出完成。运行新增检查及相关既有回归，记录本轮真实测试结果，不把旧的通过数充作本轮实测。

所有离线检查通过后提交代码与机器计划，固定实际运行 SHA。在线开始后不根据结果改规则、提示、类型或上限。基础设施失败保留 NOT_RUN，不将脚本退出成功当作模型成功。

## 队列、判定与额度

开发队列为 q775、q774、q771、q778，每题两臂各一条新自然运行、交错顺序；难题每槽16次、短控制每槽4次、每槽600秒，最多80次策略请求和8次封存后 judge。本轮选择发生在 confirmation-01 审阅之后，十二题均已暴露，后续不能称为未参与设计的测试集。

开发正确数严格增加、控制无正确转错误且新增正确答案有已交付原文支持，才启动另一个冻结的十二题新配对复验，最多336次策略请求和24次 judge。停止标准仍要求开发与复验均正向、复验净增至少一题、两个短控制无退化，且排除四个开发题后的八题净增至少一题。只支持这组已暴露问题上的小规模观察，不声称总体提升或统计显著。判分后独立核对核心答案及主体关系，旧正式6/12保持不变。

confirmation-01 结束时，当前1000次授权窗口已用770次、剩230次。为保留完整复验所需360次，本轮先完成离线准备，按用户追加授权等待北京时间次日00:00刷新后再启动开发队列。不会预支尚未到时的额度。

刷新使用原共享总账，新增 `autonomous-search-20260916` epoch，保留所有旧请求、旧 cap/used 和哈希；新 cap=当时实际 used+1000，旧剩余230不叠加。`prepare --epoch` 只选择计划身份，不刷新额度；真实发送仍核验总账 epoch。每次失败或未知 HTTP 发送前占账，辅助请求和 judge 同样计入。额度表示用户授权计数，不宣称已查询提供方账单。达到保留阈值后不启动无法完整支付的阶段。

## 发布

完整原始 HTTP、SQLite、逐轮模型动作、回执、原文及预算记录先在私有新目录封存；公开发布脱敏的完整轨迹、报告和哈希映射，模型输入输出和原文不改值。凭证、部署信息、生产索引路径和共享总账不上传。负结果同样提交，成功必须由真实新对照和来源审阅支持。
